# Як допомогти з lingva.lab

Про навчальну мету читайте в [README](README.md), про модулі — у [довіднику архітектури](docs/architecture.md). Ми працюємо в одному репозиторії та використовуємо pnpm.

## Одна зміна — окрема гілка і pull request

Не надсилайте коміти безпосередньо в `main`. Створіть гілку, внесіть зміни, виконайте перевірки й відкрийте pull request (PR) до `main`:

```sh
git switch main
git pull --ff-only
git switch -c content/french-unicode
pnpm install --frozen-lockfile
```

У PR коротко поясніть навчальну або технічну мету, наведіть приклад зміни й результати перевірок. Злиття в `main` запускає публікацію. Не додавайте до репозиторію справжні студентські відповіді, звіти, персональні дані або секретні ключі.

## Де змінювати матеріали

- Приклади певної мови: `content/tracks/fr/language.js`, `de/language.js` або `en/language.js`. Матеріали академічного документа — у `content/tracks/<мова>/documents.js`, набори форматів — у `content/tracks/<мова>/formats.js`.
- Порядок і склад розділів: `content/tracks/<мова>/foundations.js`. Кожен маршрут має власний список.
- Спільний дизайн вправ: `content/shared/chapters/`. Зміна тут може вплинути на всі маршрути, які використовують цей розділ.
- Назви кнопок та інший текст інтерфейсу: `src/i18n/uk.js`. Англійського інтерфейсу наразі немає.

Є три способи додати розділ до маніфесту:

1. Використати спільну функцію розділу з власними мовними прикладами.
2. Викликати `adaptChapter(base, adapter)` і явно повернути змінений розділ. Так можна замінити одну вправу або додати практику для однієї мови.
3. Написати власний розділ за допомогою `defineChapter(...)` або готового об’єкта. Це підходить, коли навчальна задача істотно відрізняється.

Приклади всіх трьох способів є в [архітектурному довіднику](docs/architecture.md). Власні розділи зберігайте в `content/tracks/<мова>/chapters/`. Додавайте новий тип редактора або перевірки лише тоді, коли наявні типи не підходять.

## Як додати вправу

1. Виберіть маршрут і розділ. Додайте вправу до його `tasks`; кількість і порядок можуть змінюватися.
2. Задайте зрозумілий ID, наприклад `unicode-normalization-audit`. Використовуйте малі латинські літери, цифри та дефіси, до 100 символів. ID вправи має бути унікальним у межах маршруту. Не утворюйте його з номера розділу чи позиції вправи.
3. Задайте `type`, `title`, `prompt`, відповідь або критерії, пояснення й підказку. Для текстів певною мовою використовуйте матеріали її `language.js`.
4. Почніть із `revision: 1`. У `defineChapter` це типове значення; він також задає `required: true` та XP. Для добровільної практики вкажіть `required: false`. Приховані виклики теж добровільні.
5. Перевірте, що правильна відповідь досяжна, помилка пояснюється, а мовні приклади коректні. Якщо є кілька правильних варіантів, задайте `multiple: true` і масив індексів у `answer`. Індекси починаються з нуля.

Для поетапної майстерні, як у розділі 1, вправа також задає `stage`, орієнтовні `minutes` і `lesson` з українськими поясненнями, прикладом та кроками. Маніфест майстерні описує етапи й навчальні файли. Коли додаєте вправу, узгодьте етап, обов’язковість і сумарний час; `pnpm check:content` перевірить ці зв’язки. Час є оцінкою навантаження, а не умовою доступу.

Для розділу 6 спільний дизайн і пояснення містяться в `content/shared/chapters/information-search/`, а мовні значення – в `content/tracks/<мова>/search.js`. Нові живі пошуки оцінюйте за задокументованими рішеннями та джерелами через `portfolio` з рубрикою. Не задавайте єдиної точної відповіді для вільного запиту чи змінного порядку результатів. Короткі автоматичні перевірки мають спиратися на сталу умову/картку. Оновіть [текст розділу для перегляду](docs/chapter-six-review.md) скриптом `scripts/export-chapter-review.mjs` після правок.

Опис майбутнього розділу задається в `content/shared/outline/chapters.js`, приклади певної мови — у `content/tracks/<мова>/outline.js`. Маніфест кожного маршруту окремо вибирає та впорядковує елементи `chapterCatalog`. `status: "planned"` означає `required: false`, `tasks: []`, `time: 0` і заповнений `overview`: мета, основи, практика, застосування, приклад, примітка та пов’язані теми. Такий опис доступний для читання й не має оцінювання. Щоб додати справжні вправи, приберіть `planned`, задайте час, обов’язкові вправи та перевірте вплив на завершення курсу. Оновлюйте [програму](docs/course-outline.md) скриптом `scripts/export-course-outline.mjs`.

Новий базовий або поглиблений маршрут отримує власний ID, наприклад `fr-advanced`, власний маніфест і запис у `content/registry.js`. Його прогрес зберігатиметься окремо. У маніфесті також задаються відзнаки та, за потреби, опис оцінювання.

Для порівняння окремих символів у поясненні можна додати `lesson.symbols: [{ text: "␠", label: "Позначка пробілу" }]`. Сайт покаже великий знак і звичайний підпис. Текст зразків входить до історичного знімка пояснення; не вставляйте HTML у матеріали. Позначку ␠ відрізняйте від справжнього пробілу U+0020.

## Перевірки перед PR

Для CSV-вправ використовуйте `type: "exact"`, `checker: "csv"`, `expectedRows` як масив записів із текстовими полями та `answer` як приклад правильної відповіді. Допоміжна функція `csv(...)` у майстерні форматів створить такий приклад через спільний серіалізатор `content/shared/csv.js`. Перевірка порівнює прочитані значення, а історія зберігає початкове введення. Не замінюйте це простим порівнянням рядків. Імпортована таблиця й справжні зовнішні дії перевіряються викладачем.

Файли набору за замовчуванням мають UTF-8. Для оголошеної навчальної UTF-16LE-копії задайте `encoding: "utf16le"`: ZIP міститиме справжні байти з BOM, а на сторінці залишиться декодований перегляд. Перевіряйте збереження значень після перетворень незалежним читачем. Для текстового перегляду розділу 3: `node scripts/export-chapter-review.mjs de-foundations data-formats > docs/chapter-three-review.md`, потім Prettier.

Потрібні Node.js 24 або новіший, pnpm із `package.json` та Python 3 для локального сервера.

```sh
pnpm format
pnpm check
pnpm exec playwright install chromium
pnpm test:browser
```

`pnpm check` перевіряє матеріали, стиль, форматування, модульні тести та збірку. Браузерні тести проходять реальні вправи, звіти, імпорт, час роботи, відгуки та мобільні макети. Для вже встановленого Chrome можна виконати `PLAYWRIGHT_CHANNEL=chrome pnpm test:browser`. CI виконує обидві перевірки в кожному PR.

## Матеріали словникової майстерні

Приклади розділу 8 зберігаються у `content/tracks/<мова>/dictionaries.js`, спільні вправи – у `content/shared/chapters/digital-dictionaries/`. Картки E1/E2/U1 створені для навчання: не приписуйте їх реальним словникам. Для нової вправи задайте сталий змістовий ID `digital-dictionaries-*`, етап, час читання й практики, пояснення та джерело. Номери значень живого словника не використовуйте як автоматичний ключ: перевіряйте підготовлені умови, а зовнішні докази оцінюйте за критеріями подання. Оновіть текст для перегляду командою `node scripts/export-chapter-review.mjs de-foundations digital-dictionaries > docs/chapter-eight-review.md`, відформатуйте його й виконайте перевірки вище.

Словниковий проєкт задається як `portfolio` з `editor: "dictionary"` і `dictionaryLanguage` поточної траєкторії. Перевірка даних міститься в `src/tools/lexicon.js`, форма – в `src/ui/exercises/lexicon.js`; вміст не залежить від DOM. Дані зберігаються у наявному `method`, тому не додавайте неперевірених полів у прогрес. Зв’язки посилаються на сталі ID значень, новий запис не отримує видалений ID. `taskIds` у відзнаці дозволяє відзначити окремий добровільний проєкт. Для перевірки форми використовуйте сценарій `tests/browser-dictionaries.mjs` і збережіть поведінку без обов’язкового виконання проєкту.

## Як змінювати вже опубліковані вправи

Майстерня розділу 4 бере мовні значення з `content/tracks/<мова>/typography.js`. Для точної Unicode-вправи задайте `type: "exact"`, `checker: "unicode"`, `normalization: "NFC"` (канонічна еквівалентність без згортання пробілів) або `"none"` (саме задана послідовність). `inspector: "typography"` додає перегляд; `palette` – до 24 окремих кодових точок, `probe` – необов’язкова буквальна пошукова проба. Звичайний `exact` не перевіряє відмінність типів пробілу. Не використовуйте його для таких навчальних умов. Розкладка й IPA-панель не визначають вимову; указуйте конвенцію. Для перегляду тексту: `node scripts/export-chapter-review.mjs de-foundations unicode > docs/chapter-four-review.md`, потім Prettier.

Після початку навчання ID не можна повторно використати для іншої задачі. Переставлення вправи не змінює її ID. Нова навчальна задача отримує новий ID; зміна умов, варіантів або правил перевірки тієї самої задачі збільшує `revision`. Виправлення оформлення, яке не змінює значення, цього не потребує.

Історичні спроби містять знімок умов і варіантів. Не переписуйте їх і не перевіряйте автоматично за новими відповідями. Старі записи залишаються в резервних копіях; після зміни revision студент має виконати поточну редакцію. XP за той самий ID вдруге не нараховуються.

Для зміни формату даних потрібні окрема міграція, незмінний тестовий приклад старого формату й перевірка імпорту та експорту. Деталі — у [правилах версій і збереження прогресу](docs/versioning.md). Згадуйте вплив на студентські записи в описі PR.

### Термінологія та глосарії (розділ 10)

Мовні тексти й назви зберігайте в `content/tracks/<мова>/terminology.js`, спільні вправи – у `content/shared/chapters/terminology/`. Не змішуйте поняття, окрему назву та стан перевірки. Для навчальних українських відповідників явно зазначайте проєктні межі: їх не слід видавати за офіційно затверджені назви IATE або ISO. Авторські матеріали й справжні джерела позначайте окремо; невиконаний пошук залишається планом.

Підсумковий CSV має один рядок на поняття, а дві малі CSV-вправи – один рядок на назву; цей вибір одиниці обліку пояснено студентам. CSV перевіряється за значеннями полів, тому різні коректні способи взяття в лапки приймаються. Для досьє автоматично перевіряється структура; кількість понять, докази й наукову якість оцінює викладач. Нових типів вправ або формату прогресу для цієї майстерні немає. Після редагування оновіть `docs/chapter-ten-review.md` експортером і виконайте звичайні перевірки.

### Контекстні двомовні ресурси (розділ 9)

Мовні приклади додавайте в `content/tracks/<мова>/bilingual.js`, спільні вправи – у `content/shared/chapters/bilingual-contexts/`. Позначайте авторські навчальні пари й справжні джерела окремо; не вимагайте стабільного рейтингу, кількості живих результатів або другої іноземної мови. Передбачайте маршрут за навчальними картками. У досьє перевіряється структура; відповідність перекладу й доказів оцінює викладач.

Для інспектора `alignment` потрібні обидва списки сегментів із унікальними ID та повний текст тих самих пар у `lesson.example`: він потрапить до історичної умови й звіту. Перегляд не подає відповіді; звичайний exact-checker перевіряє введений ID. Не змінюйте ID вже опублікованої вправи лише через її позицію; зміни умови позначайте revision за правилами версіювання. Після редагування оновіть `docs/chapter-nine-review.md` через наявний експортер, виконайте `pnpm check` і браузерні перевірки.
