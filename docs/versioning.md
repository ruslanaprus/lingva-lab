# Версії продукту і студентських даних

## Версія продукту

Перша опублікована версія — `1.0.0`. Версія `2.0.0` запровадила сталі ID та формат прогресу 2. Ця гілка готує сумісне розширення `2.1.0`: майстерню першого розділу. Формат прогресу залишається 2; поле `definition.prompt` нових спроб першого розділу містить також текст пояснення й навчального прикладу цієї редакції. Нових полів у збережені записи не додано; попередні копії приймаються. Історію вже опублікованої версії не переписуємо. Зміна номера в `package.json` сама собою не створює реліз і не публікує сайт.

Використовуємо три числа: **major.minor.patch**, наприклад `2.1.3`.

- **Patch** — виправлення помилки або пояснення без несумісної зміни даних.
- **Minor** — нова сумісна можливість, додаткові вправи або новий маршрут.
- **Major** — несумісна зміна формату, експорту або публічної поведінки.

Чернетки змін описуємо в `CHANGELOG.md` під `Unreleased`. Перед релізом узгоджуємо номер, опис і перевірки в PR. Після злиття можна створити тег на кшталт `v2.0.0` та GitHub Release. Теги опублікованих версій не переносимо на інші коміти.

Збірка записує версію з `package.json` у `dist/src/version.js`. Локальний незбираний сайт використовує позначку `development`. Звіти містять версію застосунку й окремий номер формату звіту.

## Окремі номери для різних змін

| Поле                       | Що воно означає                                  |
| -------------------------- | ------------------------------------------------ |
| `package.json` → `version` | Версія всього продукту                           |
| Маніфест → `revision`      | Редакція програми конкретного маршруту           |
| Вправа → `revision`        | Редакція умов і правил конкретної вправи         |
| `STORAGE_SCHEMA_VERSION`   | Структура резервної копії та локального прогресу |
| `REPORT_SCHEMA_VERSION`    | Структура JSON-звіту                             |
| `GRADER_VERSION`           | Редакція спільного механізму перевірки           |

У `2.1.0` програма базових маршрутів і перший розділ мають revision 2. Попередні чотири короткі вправи збережено зі сталими ID; нове подання повного README має `workspace-portfolio`, revision 2. Давнє подання лишається в історії, але не завершує нову редакцію. Версія перевірки — 2: додано формальні вимоги до нового README без переоцінювання старих спроб.

Зміна одного номера не повинна автоматично змінювати всі інші. Додавання розділу зазвичай збільшує revision маніфесту й minor продукту, але не потребує нового формату сховища. Виправлення правил спільної перевірки потребує перегляду `GRADER_VERSION` та revision усіх вправ, для яких змінилося значення правильної відповіді.

## Що зберігає спроба

Прогрес належить ID маршруту, наприклад `fr-foundations`. Усередині нього вправа має сталий ID, наприклад `unicode-normalization-inspector`. Позиція на сторінці не є частиною ID.

Кожна спроба містить дату, точну відповідь, результат, пояснення перевірки, кількість підказок, `graderVersion` і знімок `definition`. Знімок містить ID, розділ, revision, тип, назву, умови, XP і, для вибору, варіанти відповіді. `selectedOptions` містить технічний індекс від 0, номер від 1 і текст обраного варіанта. Правильна відповідь з матеріалів до цього знімка не додається.

Нові умови не замінюють старий знімок. Імпорт не перевіряє історичні відповіді за поточним ключем відповідей. Завершення поточної вправи враховує спроби її поточної revision. Після зміни revision стара успішна спроба залишається в історії, але поточну редакцію потрібно пройти знову. XP за один ID у межах маршруту надаються один раз.

Якщо вправу прибрано, її записи залишаються в резервній копії та звіті відповідного розділу з позначкою архівної вправи. Якщо прибрано весь розділ або маршрут, записи також залишаються в резервній копії, але не блокують поточне навчання. Окремого переглядача архівних курсів наразі немає. Перенесення вправи між розділами потребує перегляду звітів: старі спроби зберігають початковий розділ у знімку.

## Перехід від першої версії

Студенти ще не почали навчання, тому для переходу на нові ID старий тестовий прогрес **не мігрується**. Новий ключ — `lingva-lab:v2`. Старий `lingva-lab:v1` не видаляється; інтерфейс дозволяє завантажити його початковий вміст для відновлення або аналізу. Імпорт резервної копії формату 1 повертає пояснення, що вона не підтримується. Чернетки старих відгуків теж залишаються в окремому старому ключі.

Це одноразове рішення до початку навчання. Для майбутніх версій діє наведена нижче процедура.

## Майбутня зміна формату

1. Опишіть, які поля змінюються і що має статися зі старими відповідями, часом, XP та видаленими вправами.
2. Додайте чисту функцію переходу з N до N+1 у `STORAGE_MIGRATIONS` у `src/persistence/state.js`. Вона не звертається до DOM або localStorage, не видаляє історію і не переоцінює спроби.
3. Збільште `STORAGE_SCHEMA_VERSION`. Звичайне оновлення схеми може використовувати той самий ключ `lingva-lab:v2`: номер схеми всередині даних визначає послідовність міграцій. Новий ключ потрібний лише для свідомого окремого переходу з планом пошуку старого ключа.
4. Збережіть незмінний приклад попереднього формату в `tests/fixtures/`. Не переписуйте його за поточною моделлю. Перевірте послідовну міграцію, збереження історії, повторний експорт та імпорт.
5. Перевірте пошкоджену копію і копію з майбутньої версії. У разі помилки оригінал має лишитися доступним для завантаження, а автоматичне збереження не повинно його затерти.
6. До публікації поясніть перехід у changelog і PR. За потреби залиште тестовий експорт до оновлення та шлях повернення.

Поточне завантаження відхиляє невідомі поля й несумісні версії. Якщо основний запис пошкоджено, застосунок відкриває чисту сесію без перезапису оригіналу; збереження відновлюється після явного імпорту сумісної копії. Не визначайте потрібну міграцію лише за номером релізу продукту.
